# Artifact — EMR 연동 검토 브리프

> 비트컴퓨터 미팅용 요약본. 상세 기술 계획은 [`security-remediation-plan.md`](./security-remediation-plan.md) 참조.
>
> 작성 기준일: 2026-08-13 · **갱신: 2026-09-17** · 코드 기준: `dev`

---

## 1. 무엇을 만들었나

**피부과 진료 워크플로 전체를 커버하는 AI 보조 진단 시스템.**
대기실 키오스크에서 예비분석 → 진료실에서 정식 분석 → KCD 상병코드 확정 → 처방 저장 →
제증명 발급 → 환자가 QR 로 문서 확인까지 하나의 도메인 모델로 이어진다.

| 구성 | 기술 |
|---|---|
| 프론트엔드 | React 19 + TypeScript + Tailwind (nginx 서빙) |
| 백엔드 | Spring Boot 3.5 / Java 21 + JPA + MySQL 8.0 |
| AI 추론 | FastAPI + PyTorch (EfficientNet-B0, 8클래스 — HAM10000 7종 + 염증성) |
| 배포 | EC2 + Docker Compose + Caddy(HTTPS), GitHub Actions 자동 배포 |

## 2. 차별점 — 먼저 봐주셨으면 하는 것

### 2-1. Grad-CAM 기반 설명가능성 (외부 라이브러리 없이 구현)

AI 도입에서 가장 큰 저항은 "블랙박스"다. 저희는 모델이 **어느 부위를 보고 판단했는지**를
원본 해상도 히트맵으로 오버레이해 의사에게 제시한다.

`grad-cam` 라이브러리나 OpenCV 없이 **순수 PyTorch + Pillow로 직접 구현**했다
(`fastapi/main.py`의 `_compute_gradcam()` / `_render_gradcam_overlay()`).
의존성이 적을수록 온프레미스 반입 심사가 쉬워진다는 판단이었다.

### 2-2. 실제 코드 체계 연동 — KCD 상병코드 + 약품 마스터

더미 데이터가 아니라 **실제 KCD 상병코드와 약품 마스터를 적재해 사용**한다.
14MB 엑셀을 메모리 폭발 없이 적재하기 위해 **POI SAX 스트리밍 파서**를 직접 구현했다
(`DataInitializer.java:300-377`).

### 2-3. 진료 워크플로의 도메인 모델화 — Visit 상태 머신

```
RECEIVED → IN_PROGRESS → ANALYZING → ANALYZED → DIAGNOSED → PRESCRIBED → COMPLETED
                                                          ↘ CANCELLED
```

상태 전이가 엔티티 내부 메서드로 캡슐화되어 있어(`Visit.java:59-151`),
잘못된 순서의 전이는 도메인 레벨에서 거부된다.

특히 **"처방 저장이 곧 진단 확정"**이라는 실제 진료 행위를 한 트랜잭션으로 묶었다
(`confirmDiagnosisAndPrescribe()`). 클라이언트가 두 번의 API 호출로 조립하면
"진단 확정만 성공하고 처방은 실패"한 중간 상태가 남기 때문이다.
AI 분석을 건너뛰고 육안으로 바로 처방하는 경로도 같은 메서드가 처리한다.

### 2-4. 저장소 추상화 — 온프레미스 전환이 인터페이스 교체만으로 가능

`ImageStorageService` 인터페이스 하나에 `S3ImageStorageService` / `LocalImageStorageService`
두 구현이 붙어 있고, 설정값 하나로 전환된다.

```properties
image.storage.type=${IMAGE_STORAGE_TYPE:s3}   # local 로 바꾸면 온프레미스
```

**병원은 대부분 환자 이미지의 외부 반출을 허용하지 않는다.** 이 추상화는 처음부터
그 제약을 염두에 두고 설계한 것이며, 실제 도입 협의에서 가장 먼저 필요한 카드라고 본다.

### 2-5. 키오스크 — 대기 시간을 예비분석에 활용

접수 후 대기 시간에 태블릿으로 환부를 촬영하면 의사가 진료실에서 미리 결과를 본다.
Visit의 정식 FSM과 **완전히 분리된 사이드 채널**로 설계해, 예비분석 실패가 정식 진료 흐름에 영향을 주지 않는다.

접수 시 발급하는 **base62 12자리 `SecureRandom` 토큰**으로 QR을 만든다 —
`visit_id`가 순차 정수라 같은 LAN에서 추측 가능하다는 판단에서 나온 설계다.

### 2-6. 제증명 — LLM에 "사실을 적을 자리"를 주지 않는다

진단서·소견서·진료확인서·처방전을 실제로 발급한다. 문구 초안은 LLM이 만들지만,
**환자명·상병코드·약품명 같은 사실 정보는 DB 값을 그대로 채운다.**

구현 방식이 요점이다. "지어내지 말라"고 프롬프트에 적는 대신,
**LLM 응답 스키마에서 사실 필드를 아예 제거**했다(`CertificateDraftResponse`).
모델이 병명을 지어내도 **그 값이 문서에 들어갈 경로가 없다.** 프롬프트 지시는 지켜지지
않을 수 있지만, 없는 필드는 채워질 수 없다.

응답에는 `disclaimer`("AI가 작성한 초안입니다. 반드시 의사가 검토·수정한 뒤 발급하십시오.")가
항상 포함되어, 프론트가 고지를 누락할 방법이 없다.

발급 문서에는 연번과 QR이 찍히고, 환자는 로그인 없이 **QR + 생년월일 2요소**로 원문을
연다. 토큰당 5회 실패 시 10분 잠금이다.

### 2-7. 인쇄 — 병원 내부망에 구멍을 내지 않는 방향

프린터는 접수 데스크 PC에 물려 있고 서버에는 없다. 흔한 구현은 서버가 그 PC를 호출하는
것인데, 그러려면 **내부망에 인바운드 경로를 열어야 한다.** 병원에서 통과되기 어렵다.

방향을 뒤집었다. **접수 데스크의 에이전트가 서버로 접속해 인쇄 작업을 가져간다**(롱폴링).
열어야 할 포트도, 터널도, 고정 주소도 없다.

- `X-Agent-Instance` **펜싱 토큰**으로 같은 문서가 두 번 인쇄되는 것을 막는다 —
  의료 문서 중복 출력은 실제 사고다.
- **인쇄 실패는 예외를 던지지 않는다.** 프린터가 꺼져 있어도 접수·발급은 그대로 진행된다.

## 3. 현재 상태 — 정직하게

저희는 최근 코드베이스 전체에 대한 **자체 보안·품질 감사를 수행**했고,
설계 원칙은 있었으나 **아직 전면 적용되지 않은 지점들**을 찾아 게이트별로 닫는 중이다.

가장 대표적인 예가 위 2-5의 키오스크 토큰이었다. 순차 ID 노출을 막겠다는 원칙은 세워 설계까지
했지만 **조회 엔드포인트 일부에 적용되지 않은 상태**였고, 감사에서 그 격차를 발견해 닫았다.

이 브리프에 감사 결과를 그대로 담는 이유는, **결함을 숨기는 것보다 파악하고 있다는 사실이
더 신뢰를 준다고 판단**했기 때문이다. 필요하시면 전체 감사 문서도 공유 가능하다.

### 개선 로드맵

| 게이트 | 내용 | 상태 |
|---|---|---|
| **G0** | 인증 기반 정비 (서명키 외부화, 권한 상승 차단) | ✅ **구현 완료 · 리뷰 중** |
| **G1** | AI 추론 동시성 정합성 | ✅ **구현 완료 · 재현 테스트로 검증** |
| **G2** | 인가 전면 적용, 외부 호출 타임아웃·트랜잭션 경계 | ✅ **구현 완료** (`@PublicEndpoint` 표식 + 인가 테스트) |
| **G3** | 감사 추적, 처방 원본 보존, AI 출력 고지 | ⚠️ **부분 완료** — 고지·PII 마스킹 완료 / **감사 추적·원본 보존 미구현** |
| **G4** | HTTPS, 백업·복구, CI, 모니터링 | ⚠️ **부분 완료** — HTTPS·CI·자동배포 완료 / **백업·모니터링 미착수** |

G1은 **고치기 전에 재현 테스트를 먼저 작성해 실패를 확인하고, 수정 후 통과를 확인하는 방식**으로 진행했다.
동시 40요청 기준 오염 20건 → **0건**. 재현 스크립트는 저장소에 함께 커밋되어 회귀 테스트로 남는다.

**남은 두 가지를 분명히 해둔다.** G3의 감사 추적과 처방 원본 보존은 설계만 있고 코드가 없다.
아래 4절의 답변 중 그 둘은 **지난 미팅 이후로 달라진 것이 없다** — 진척된 항목과 섞이지 않도록
따로 적는다.

## 4. 예상 질문에 대한 현재 답변

### Q. 접속기록(감사 추적)은 남습니까?

**현재: 여전히 없습니다.** 의료법 제22조와 개인정보보호법 시행령 제30조(접속기록 2년 보관)상
필수 요건임을 인지하고 있으나, **아직 코드가 없다.** 남은 항목 중 우선순위가 가장 높다.

설계 방향은 Spring AOP `@Around` + `@Auditable` 애노테이션으로,
환자 데이터에 접근하는 모든 메서드를 가로채 `audit_log`(actor_id, action, resource_type,
resource_id, timestamp, ip)에 자동 기록하는 구조다. 컨트롤러마다 로깅 코드를 흩뿌리면
반드시 누락이 생기므로, **애노테이션 하나만 붙이면 되는 형태**로 만든다.

### Q. 진료기록 수정 시 원본은 보존됩니까?

**현재: 재처방 시 이전 처방이 물리 삭제됩니다. 이 부분은 아직 그대로다.**
`version` / `superseded_by` / `is_active` 컬럼 추가로 전환할 계획이며, 물리 삭제 대신
`is_active=false` + 새 버전 insert 방식이다.

증명서는 발급 시점의 내용을 자체 레코드로 보관하고 재발급·무효화 이력도 남기므로
**발급된 문서 자체는 보존된다.** 다만 그 근거가 된 처방이 덮어써지는 구조라,
"당시 처방"을 DB에서 되짚는 것은 아직 불가능하다.

### Q. 환자 정보가 외부 LLM으로 나갑니까?

**현재: 처방 코멘트 생성 시 접수 메모가 Google Gemini API로 전송됩니다.**
개인정보보호법 제28조의8상 국외 이전 별도 동의가 필요한 사안임을 인지하고 있다.

- **단기(완료)**: 전송 전 이름·전화번호 등 식별자를 마스킹하는 `PiiMasker` 를 적용했다.
  처방 코멘트와 증명서 초안 두 경로 모두 이 레이어를 거친다
- **중기**: 국내 LLM(HyperCLOVA X, EXAONE 등) 또는 온프레미스 sLLM으로 전환 실험.
  현재 RAG 파이프라인(BGE-M3)을 로컬로 구성할 계획이 있어 여기에 함께 태울 수 있다.
  Gemini는 폴백으로만 남긴다.

### Q. AI 출력의 법적 지위는?

SaMD(소프트웨어 의료기기) 해당 여부 검토가 필요한 상태로 판단하고 있으며, 그 전제 위에서
고지를 **구조로** 걸었다.

- 증명서 AI 초안 응답에 `disclaimer` 필드가 **항상** 포함된다
  ("AI가 작성한 초안입니다. 반드시 의사가 검토·수정한 뒤 발급하십시오").
  프론트가 실수로 고지를 누락할 방법이 없다.
- 키오스크 예비분석 화면에는 "AI 보조 참고용 결과이며 의학적 진단이 아님"을 상시 노출한다.
- 저신뢰 결과는 **차단하지 않고 경고만 붙인다.** 차단이 오히려 악성 병변을 놓치게 만든다는
  것을 홀드아웃 2,857장으로 측정했다 — 근거 수치는 `fastapi/tests/README.md`.

식약처 SaMD 가이드라인 검토는 팀 명의로 정리 중이다.

### Q. 온프레미스 배포가 가능합니까?

**저장소 계층은 가능하다** (2-4 참조). 설정값 하나로 S3 ↔ 로컬 디스크가 전환된다.
DB(MySQL)와 AI 추론 서버(FastAPI)도 모두 컨테이너라 폐쇄망 반입에 구조적 장애가 없다.

**남은 것은 LLM 의존성 하나**다. 위 Q3의 중기 계획이 완료되면 완전 폐쇄망 구성이 가능해진다.

### Q. 테스트 커버리지는요?

**지난 미팅 때 답변은 "사실상 0, 컴파일도 되지 않음"이었다. 그 상태는 해소했다.**

- **CI를 먼저 세웠다.** PR과 `main`/`dev` 푸시마다 백엔드·프론트·AI 세 job이 병렬로 돈다
  (`.github/workflows/ci.yml`). 당초 계획에서는 마지막 단계(G4)였으나,
  "깨진 것을 감지할 장치가 없다"는 것이 진짜 문제라고 판단해 앞으로 당겼다.
- 그다음 **깨지면 환자에게 영향이 가는 경로**부터 테스트로 잠갔다. 현재 백엔드 테스트
  클래스 11개이며, 커버리지 숫자보다 **무엇을 잠갔는지**로 말하는 편이 정확하다.

| 잠근 것 | 테스트 |
| --- | --- |
| 인가 — 어떤 엔드포인트가 로그인 없이 열리는가 | `EndpointAuthorizationTest` |
| AI 추론 동시성 — 결과가 섞이지 않는가 | `AnalysisResilienceTest` |
| 문서 열람 잠금 — 생년월일 무차별 대입 차단 | `ShareAccessGuardTest`, `DocumentShareServiceTest` |
| 제증명 발급·초안 | `CertificateServiceTest`, `CertificateDraftServiceTest` |
| 주민번호 마스킹 · PII 마스킹 | `ResidentNumberMaskTest`, `PiiMaskerTest` |
| QR 주소 허용 목록 | `KioskBaseUrlPolicyTest` |
| CORS 허용 출처 | `CorsConfigTest` |

AI 쪽은 성격이 달라 별도 하네스를 두었다. **고정된 홀드아웃 2,857장**에 대고
이전 모델과 같은 조건으로만 비교하며, 매번 새로 표본을 뽑는 것을 코드 가드로 막는다
(`ALLOW_NEW_HOLDOUT=False`). 표본이 바뀌면 "모델이 좋아진 것"과 "문제가 쉬워진 것"을
구분할 수 없기 때문이다. 클래스 순서 계약도 테스트로 강제한다
(`test_model_contract.py`) — 순서가 어긋나면 **오류 없이 조용히 틀린 병명이 나온다.**

**남은 것 두 가지는 그대로다.** 프론트엔드 테스트는 아직 없다. 그리고 테스트는 H2
인메모리 DB에 JPA가 스키마를 만드는 반면 운영은 MySQL이라, **두 스키마가 서로 다른
경로로 만들어진다.** Testcontainers 전환이 필요하다.

### Q. 백업·복구는?

**현재: 여전히 전략 없음.** HTTPS와 CI·자동배포는 섰지만 백업은 손대지 못했다.
자동 백업뿐 아니라 **복구 리허설까지** 포함해야 의미가 있다고 보고 있다
(백업만 있고 복구가 안 되는 사례가 흔하므로).
