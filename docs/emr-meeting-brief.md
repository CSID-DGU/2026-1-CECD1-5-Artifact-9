## 1. 무엇을 만들었나

**피부과 진료 워크플로 전체를 커버하는 AI 보조 진단 시스템.**
대기실 키오스크에서 예비분석 → 진료실에서 정식 분석 → KCD 상병코드 확정 → 처방 저장 → 소견서 발급까지
하나의 도메인 모델로 이어진다.

| 구성 | 기술 |
|---|---|
| 프론트엔드 | React 19 + TypeScript + Tailwind (nginx 서빙) |
| 백엔드 | Spring Boot 3.5 / Java 21 + JPA + MySQL 8.0 |
| AI 추론 | FastAPI + PyTorch (EfficientNet-B0, HAM10000 7클래스) |
| 배포 | Docker Compose (EC2 이전 예정) |

## 2. 차별점 — 먼저 봐주셨으면 하는 것

### 2-1. Grad-CAM 기반 설명가능성 (외부 라이브러리 없이 구현)

AI 도입에서 가장 큰 저항은 "블랙박스"다. 저희는 모델이 **어느 부위를 보고 판단했는지**를
원본 해상도 히트맵으로 오버레이해 의사에게 제시한다.

`grad-cam` 라이브러리나 OpenCV 없이 **순수 PyTorch + Pillow로 직접 구현**했다
(`fastapi/main.py:58-106`). 의존성이 적을수록 온프레미스 반입 심사가 쉬워진다는 판단이었다.

### 2-2. 실제 코드 체계 연동 — KCD 상병코드 + 약품 마스터

더미 데이터가 아니라 **실제 KCD 상병코드와 약품 마스터를 적재해 사용**한다.
14MB 엑셀을 메모리 폭발 없이 적재하기 위해 **POI SAX 스트리밍 파서**를 직접 구현했다
(`DataInitializer.java:300-377`).

### 2-3. 진료 워크플로의 도메인 모델화 — Visit 상태 머신

```
RECEIVED → IN_PROGRESS → ANALYZING → ANALYZED → DIAGNOSED → PRESCRIBED → COMPLETED
                                                          ↘ CANCELLED
```

상태 전이가 엔티티 내부 메서드로 캡슐화되어 있어(`Visit.java:59-151`),
잘못된 순서의 전이는 도메인 레벨에서 거부된다.

특히 **"처방 저장이 곧 진단 확정"**이라는 실제 진료 행위를 한 트랜잭션으로 묶었다
(`confirmDiagnosisAndPrescribe()`). 클라이언트가 두 번의 API 호출로 조립하면
"진단 확정만 성공하고 처방은 실패"한 중간 상태가 남기 때문이다.
AI 분석을 건너뛰고 육안으로 바로 처방하는 경로도 같은 메서드가 처리한다.

### 2-4. 저장소 추상화 — 온프레미스 전환이 인터페이스 교체만으로 가능

`ImageStorageService` 인터페이스 하나에 `S3ImageStorageService` / `LocalImageStorageService`
두 구현이 붙어 있고, 설정값 하나로 전환된다.

```properties
image.storage.type=${IMAGE_STORAGE_TYPE:s3}   # local 로 바꾸면 온프레미스
```

**병원은 대부분 환자 이미지의 외부 반출을 허용하지 않는다.** 이 추상화는 처음부터
그 제약을 염두에 두고 설계한 것이며, 실제 도입 협의에서 가장 먼저 필요한 카드라고 본다.

### 2-5. 키오스크 — 대기 시간을 예비분석에 활용

접수 후 대기 시간에 태블릿으로 환부를 촬영하면 의사가 진료실에서 미리 결과를 본다.
Visit의 정식 FSM과 **완전히 분리된 사이드 채널**로 설계해, 예비분석 실패가 정식 진료 흐름에 영향을 주지 않는다.

접수 시 발급하는 **base62 12자리 `SecureRandom` 토큰**으로 QR을 만든다 —
`visit_id`가 순차 정수라 같은 LAN에서 추측 가능하다는 판단에서 나온 설계다.

## 3. 현재 상태 — 정직하게

저희는 최근 코드베이스 전체에 대한 **자체 보안·품질 감사를 수행**했고,
설계 원칙은 있었으나 **아직 전면 적용되지 않은 지점들**을 찾아 게이트별로 닫는 중이다.

가장 대표적인 예가 위 2-5의 키오스크 토큰이다. 순차 ID 노출을 막겠다는 원칙은 세워 설계까지 했지만,
**조회 엔드포인트 일부에 아직 적용되지 않았다.** 감사에서 그 격차를 발견했고 지금 닫고 있다.

이 브리프에 감사 결과를 그대로 담는 이유는, **결함을 숨기는 것보다 파악하고 있다는 사실이
더 신뢰를 준다고 판단**했기 때문이다. 필요하시면 전체 감사 문서도 공유 가능하다.

### 개선 로드맵

| 게이트 | 내용 | 상태 |
|---|---|---|
| **G0** | 인증 기반 정비 (서명키 외부화, 권한 상승 차단) | EC2 배포 전 완료 예정 |
| **G1** | AI 추론 동시성 정합성 | 데모 전 완료 예정 |
| **G2** | 인가 전면 적용, 외부 호출 타임아웃·트랜잭션 경계 | 미팅 전 착수 |
| **G3** | **감사 추적, 처방 원본 보존, AI 출력 고지** | 설계 완료 · 구현 착수 |
| **G4** | HTTPS, 백업·복구, CI, 모니터링 | 계획 수립 완료 |

## 4. 예상 질문에 대한 현재 답변

### Q. 접속기록(감사 추적)은 남습니까?

**현재: 없습니다.** 의료법 제22조와 개인정보보호법 시행령 제30조(접속기록 2년 보관)상
필수 요건임을 인지하고 있으며, G3에서 구현 중이다.

설계 방향은 Spring AOP `@Around` + `@Auditable` 애노테이션으로,
환자 데이터에 접근하는 모든 메서드를 가로채 `audit_log`(actor_id, action, resource_type,
resource_id, timestamp, ip)에 자동 기록하는 구조다. 컨트롤러마다 로깅 코드를 흩뿌리면
반드시 누락이 생기므로, **애노테이션 하나만 붙이면 되는 형태**로 만든다.

### Q. 진료기록 수정 시 원본은 보존됩니까?

**현재: 재처방 시 이전 처방이 물리 삭제됩니다.** 진료기록은 원본·수정본이 모두 남아야 한다는 점을
인지하고 있으며, G3에서 `version` / `superseded_by` / `is_active` 컬럼 추가로 전환한다.
물리 삭제 대신 `is_active=false` + 새 버전 insert 방식이다.

부가 효과로, 소견서를 나중에 재발급할 때 **"당시 처방"을 정확히 복원**할 수 있게 된다.

### Q. 환자 정보가 외부 LLM으로 나갑니까?

**현재: 처방 코멘트 생성 시 접수 메모가 Google Gemini API로 전송됩니다.**
개인정보보호법 제28조의8상 국외 이전 별도 동의가 필요한 사안임을 인지하고 있다.

- **단기(G3)**: 전송 전 이름·전화번호 등 식별자를 마스킹하는 전처리 레이어 추가
- **중기**: 국내 LLM(HyperCLOVA X, EXAONE 등) 또는 온프레미스 sLLM으로 전환 실험.
  현재 RAG 파이프라인(BGE-M3)을 로컬로 구성할 계획이 있어 여기에 함께 태울 수 있다.
  Gemini는 폴백으로만 남긴다.

### Q. AI 출력의 법적 지위는?

현재 분석 결과에 임상 권고 성격의 문구가 포함되어 있어(`AnalysisService.java:56-64`),
SaMD(소프트웨어 의료기기) 해당 여부 검토가 필요한 상태로 판단하고 있다.

**조치 방향**: "참고용, 진단 아님" 고지를 UI뿐 아니라 **API 응답 스키마에 `disclaimer` 필드로 필수 포함**시킨다.
그러면 프론트가 실수로 고지를 누락할 방법이 없다. 식약처 SaMD 가이드라인 검토는 팀 명의로 정리 중이다.

### Q. 온프레미스 배포가 가능합니까?

**저장소 계층은 가능하다** (2-4 참조). 설정값 하나로 S3 ↔ 로컬 디스크가 전환된다.
DB(MySQL)와 AI 추론 서버(FastAPI)도 모두 컨테이너라 폐쇄망 반입에 구조적 장애가 없다.

**남은 것은 LLM 의존성 하나**다. 위 Q3의 중기 계획이 완료되면 완전 폐쇄망 구성이 가능해진다.

### Q. 테스트 커버리지는요?

**현재 낮습니다.** 백엔드 통합 테스트 1건 수준이며 프론트엔드 테스트는 없다.

다만 무작정 커버리지 숫자를 올리기보다, **인증/인가 → Visit FSM 상태 전이 → 처방 저장 경로**
세 축을 먼저 통합 테스트로 잠그는 것을 목표로 잡았다. 이 세 가지가
(a) 진행 중인 보안 수정의 회귀 테스트로 그대로 재사용되고,
(b) FSM은 이미 8상태 설계가 있어 케이스 도출이 빠르며,
(c) **핵심 임상 워크플로를 보증한다**고 말할 수 있는 가장 짧은 경로이기 때문이다.

한 가지 선행 과제가 있다. 현재 테스트는 H2 인메모리 DB에 JPA가 스키마를 생성하는 반면
운영은 MySQL에 수동 DDL을 적용해, **두 스키마가 서로 다른 경로로 만들어진다.**
Testcontainers로 전환해 실제 MySQL 스키마를 검증하도록 바꾸는 것이 먼저다.

### Q. 백업·복구는?

**현재: 전략 없음.** G4 항목이며, 자동 백업뿐 아니라 **복구 리허설까지** 포함해야
의미가 있다고 보고 있다(백업만 있고 복구가 안 되는 사례가 흔하므로).

## 5. 협의하고 싶은 것

1. **EMR 연동 인터페이스** — 표준(HL7 FHIR 등) 기반이 가능한지, 아니면 벤더 고유 규격인지
2. **온프레미스 요구 수준** — 완전 폐쇄망인지, 아웃바운드 일부 허용인지
   (LLM 전환 우선순위가 여기서 갈린다)
3. **감사 로그 보관 요건** — 법정 최소치(2년) 외에 실무상 추가 요구가 있는지
4. **SaMD 판단** — 현재 기능 범위가 의료기기 인허가 대상인지에 대한 실무 관점 의견
5. **파일럿 가능성** — 실제 진료 환경에서 검증해볼 여지가 있는지

## 6. 요약

- **팔 만한 것**: 설명가능 AI(Grad-CAM), 실제 코드 체계 연동, 진료 워크플로의 정확한 도메인 모델링,
  온프레미스 전환 가능한 저장소 설계
- **아직 부족한 것**: 감사 추적, 진료기록 원본 보존, 국외 이전 통제, 테스트 보증 —
  **모두 인지하고 있고 게이트별 계획이 있다**
- **저희가 원하는 것**: 실무 관점에서 "이건 이렇게 하면 병원에서 안 받는다"는 지적
