# 특허 전략 — 현재 시스템의 출원 가능 요소와 보강 아이디어

> 작성일 2026-09-17 · 코드 기준 `kwon/print` 브랜치
> 논문 전략은 별도 문서: `docs/ksc2026-paper-strategy.md`

---

## 0. 먼저 — 시간이 걸린 판단 하나

**특허로 쓸 만한 게 있다.** 다만 있는 곳이 예상과 다르다.

AI 모델 쪽(EfficientNet 분류, Grad-CAM, 임계값)은 **특허가 어렵다.** 전부 공지된 기법이고,
"의료 영상에 딥러닝을 적용한다"는 조합은 이미 수천 건이 출원돼 있다.

반대로 **AI가 아닌 부분** — 클라우드 서버가 방화벽 뒤 프린터를 다루는 방식, LLM이
의료 문서를 쓸 때 거짓말을 못 하게 막는 구조, 진료 흐름을 건드리지 않고 대기실 분석을
끼워 넣는 방식 — 이쪽이 **구체적인 기술적 수단을 가진 문제 해결**이라 특허 적성이 훨씬 좋다.

> 캡스톤 팀이 흔히 하는 실수가 "우리 AI 모델을 특허 내자"인데, 그건 거의 항상 거절된다.
> **특허는 "무엇을 만들었나"가 아니라 "어떤 기술적 문제를 어떤 구체적 수단으로 풀었나"를 본다.**

아래는 후보 5개의 평가, 청구항 골격, 그리고 **특허성을 높이려면 지금 추가로 구현할 것** 5가지다.

## 1. ⚠️ 출원 전에 반드시 확인할 것 3가지

### ① 공개 저장소 = 자기 공지 = 신규성 상실

특허는 **출원일 기준으로 세상에 없던 것**이어야 한다. 그리고 **본인이 공개한 것도
선행기술이 된다.** GitHub 공개 저장소, 학회 발표, 시연회, 블로그 전부 해당한다.

**구제 방법이 있다 — 공지예외 주장 (특허법 제30조)**

```
공개일로부터 12개월 이내에 출원하면서
"공지예외 적용 대상"임을 주장하고 증명서류를 내면
그 공개는 신규성 판단에서 제외된다
```

**단, 세 가지 함정이 있다:**

| 함정 | 내용 |
|---|---|
| **해외에는 안 통한다** | 미국은 12개월 유예가 있지만 유럽·중국은 사실상 없다. 해외 출원 계획이 있으면 **공개 전 출원이 유일한 길** |
| **12개월의 기산점** | 첫 공개일이다. 저장소를 언제 public으로 돌렸는지가 기준이 될 수 있다 |
| **증명 책임** | 언제 무엇을 공개했는지 본인이 증명해야 한다. git 로그가 증거가 된다 |

**→ 지금 할 일**: 저장소가 public인지, public이라면 **언제부터인지** 확인한다.

```bash
# 리포지토리 공개 여부와 생성일
gh repo view --json isPrivate,createdAt,pushedAt
```

### ② 학회 논문 발표도 공개다 — 순서가 중요하다

```
   ❌ 나쁜 순서:  KSC2026 발표(12월) ──────▶ 특허 출원(내년)
                                 12개월 시계가 돌기 시작

   ✅ 좋은 순서:  특허 출원 ──▶ KSC2026 발표
                  (출원일 확보 후에는 무엇을 발표해도 안전)
```

> 다행히 §4에서 제안하는 논문 주제(선택적 예측의 거절 역효과)와 특허 후보(인쇄 브로커,
> LLM 게이트)는 **겹치지 않는다.** 논문이 특허 내용을 공개하지 않으므로 순서 압박이 적다.
> 다만 논문에 시스템 구조를 자세히 쓰면 겹치기 시작하므로, **논문 §3(시스템 설명)에는
> 특허 후보 요소를 상세히 쓰지 않는 게 안전하다.**

### ③ 임시명세서 제도 — 학생 팀에게 가장 현실적인 카드

한국 특허청에는 **임시명세서 출원** 제도가 있다. 정식 청구항·도면 없이
**연구 노트나 논문 형태의 문서로 먼저 출원일을 확보**하고, 이후 기간 내에
정식 명세서로 보완하는 방식이다.

| 장점 | 내용 |
|---|---|
| 출원일을 빨리 확보 | 아이디어 단계에서 바로 날짜를 잡는다 |
| 형식 부담이 적다 | 기술 설명 문서 그대로 낼 수 있다 |
| 비용이 낮다 | 정식 출원 대비 초기 비용 절감 |

> **정확한 보완 기한과 절차는 학교 산학협력단 지식재산 담당자에게 확인한다.**
> 제도 세부는 개정될 수 있으므로 이 문서의 설명을 그대로 믿지 말 것.

### ④ 발명자와 출원인 — 학생 발명의 귀속

| 구분 | 통상적인 처리 |
|---|---|
| **발명자** | 실제로 발명에 기여한 사람 (학생 + 지도교수). **명예 발명자는 위법** |
| **출원인(권리자)** | 대부분 **산학협력단**. 학교 규정과 산학 계약에 따름 |
| **비트컴퓨터(기업 멘토)** | 산학 협력 계약에 IP 조항이 있을 가능성이 높다. **반드시 먼저 확인** |

**→ 지금 할 일**: 산학협력단 IP 담당자와 기업 멘토에게 각각 문의한다. 이게 §6 1순위다.

## 2. 후보 평가

> 평가 기준: **신규성**(같은 게 없는가) · **진보성**(통상의 기술자가 쉽게 생각할 수 없는가) ·
> **구체성**(추상적 아이디어가 아니라 기술적 수단인가) · **구현 완성도**

### 후보 1 — 아웃바운드 폴링 기반 원격 인쇄 중계 ★★★

**해결한 문제.** 클라우드에 있는 EMR 서버가 **병원 내부망 방화벽 뒤에 있는 USB 프린터**로
출력해야 한다. 병원 네트워크에 인바운드 포트를 열 수도, 고정 IP를 받을 수도, VPN을
구축할 수도 없다(현실적으로 학생 팀은 물론이고 소규모 의원도 마찬가지다).

**구현한 수단** (`backend/.../print/PrintJobQueue.java`, `PrintTransport.java`, `print-agent/`):

```
   [클라우드 서버]                      [원내 맥북 에이전트]        [USB 프린터]
        │                                      │
        │  ◀─── GET /print/jobs/next ─────────│  (아웃바운드만)
        │       (DeferredResult 롱폴링 25초)   │
        │                                      │
   인쇄 요청 발생                               │
        │  ──── 작업 즉시 반환 ───────────────▶│
        │       + X-Agent-Instance 펜싱 토큰    │──── 출력 ───▶
        │                                      │
        │  ◀─── POST /print/jobs/result ──────│
        │       (성공/실패 + 펜싱 토큰)         │
        │                                      │
   [에이전트가 죽으면]
        │  가시성 타임아웃 경과 → 작업 재배달
        │  TTL(120초) 경과 → 작업 폐기 + 즉시 "프린터 미연결" 응답
```

**여기서 단순 폴링과 다른 점이 특허성의 핵심이다:**

| 요소 | 무엇을 푸는가 |
|---|---|
| **DeferredResult 롱폴링** | 짧은 주기 폴링의 지연·부하 없이 즉시 전달 |
| **에이전트 인스턴스 펜싱** | 에이전트가 재시작해 두 개가 잠시 공존할 때 **같은 문서를 두 번 출력하는 것**을 막는다. 의료 문서에서는 중복 출력이 실제 사고다 |
| **가시성 타임아웃 재배달** | 에이전트가 작업을 가져간 뒤 죽으면 다른 에이전트가 이어받는다 |
| **작업 TTL + 무예외 실패** | 프린터가 없어도 **접수·발급 업무 흐름이 절대 멈추지 않는다**. `PrintTransport`가 예외를 던지지 않고 `PrintOutcome`만 반환하는 설계 |

**평가**

| 항목 | 점수 | 근거 |
|---|:---:|---|
| 신규성 | **중~높음** | 롱폴링·큐·펜싱은 각각 공지. **의료 문서 출력 맥락에서 이 조합**은 선행기술 조사 필요 |
| 진보성 | **높음** | "중복 출력 방지"와 "업무 흐름 무중단"이라는 **의료 도메인 특유의 요구**에서 도출된 조합 |
| 구체성 | **매우 높음** | 프로토콜 수준으로 구체적 |
| 구현 | **완료** | 실제 원격 프린터로 검증됨 |

**→ 1순위 후보.**

### 후보 2 — 사실/서술 분리 LLM 의료문서 생성 게이트 ★★★

**해결한 문제.** LLM으로 진단서 초안을 만들면 **없는 병명·없는 날짜·없는 코드를
그럴듯하게 지어낸다(환각).** 의료 문서에서 이건 허위진단서 작성이 될 수 있는 사안이다.
"프롬프트로 조심시키기"는 보장이 아니다.

**구현한 수단** (`backend/.../certificate/CertificateDraftService.java`):

```
  진료 데이터(DB)
      │
      ├──── 사실 필드 ────────────────────┐   LLM에 "입력"으로는 주되
      │  병명, KCD 코드, 진료일,          │   "출력 스키마"에는 아예 칸이 없다
      │  환자 식별정보                     │
      │                                    ▼
      │                            ┌───────────────┐
      ├──── PiiMasker ────────────▶│  Gemini API   │
      │     (외부 전송 전 마스킹)    │  temp=0.2     │
      │                            └───────┬───────┘
      │                                    │ JSON 응답
      │                                    ▼
      │                        ┌────────────────────────┐
      │                        │ 서술 필드만 수용        │
      │                        │ (소견·경과·안정기간)    │
      │                        └───────────┬────────────┘
      │                                    │
      └────────── DB의 사실 ───────────────┤
                                           ▼
                                   최종 문서 조립
                          (병명·코드·날짜는 100% DB 값)
```

**핵심 기술적 수단**: LLM 응답 스키마에서 **사실 필드를 구조적으로 제거**한다.
모델이 병명을 지어내도 **그 값이 들어갈 칸이 없어서** 문서에 반영될 경로가 없다.
프롬프트 지시가 아니라 **데이터 경로 차단**이다.

여기에 세 가지가 더 붙는다:
- **PiiMasker**: 환자 식별정보가 외부 LLM에 도달하기 전에 마스킹 (국외이전 이슈 완화)
- **temperature 0.2**: 서술 필드의 변동성 억제
- **`CertificateDraftResponse.unavailable`**: LLM 실패 시 문서 발급이 막히지 않고
  "초안 없음" 상태로 진행 — 후보 1의 "업무 흐름 무중단"과 같은 철학

**평가**

| 항목 | 점수 | 근거 |
|---|:---:|---|
| 신규성 | **중** | "구조화 출력으로 LLM 제약"은 알려진 기법. **"사실 필드를 스키마에서 배제해 환각의 반영 경로를 차단"**이라는 구성이 관건 |
| 진보성 | **중~높음** | 의료 문서 법적 요구와 결합된 점 |
| 구체성 | **높음** | |
| 구현 | **완료** | |

**→ 2순위. §4-A 보강 아이디어와 묶으면 1순위로 올라간다.**

### 후보 3 — 진료 상태기계와 분리된 대기실 예비분석 채널 ★★

**해결한 문제.** 대기실 키오스크에서 환자가 스스로 촬영한 사진을 AI가 분석하면,
그 결과가 **정식 진료 기록**에 섞여 들어간다. 그러면 (a) 환자 자가 촬영 결과가
의무기록이 되고 (b) 키오스크 오류가 진료 흐름을 막는다.

**구현한 수단** (`kiosk/KioskService.java`, `preliminary_analysis` 테이블):

```
  정식 진료 FSM:  RECEIVED → IN_PROGRESS → ANALYZING → ANALYZED
                     → DIAGNOSED → PRESCRIBED → COMPLETED
                     │
                     │ 이 상태 전이에 전혀 관여하지 않음
                     ▼
  사이드 채널:   preliminary_analysis (별도 테이블)
                 접수별 kiosk_token 으로만 접근
                 실패해도 FSM 은 그대로
```

- 접수 시 **base62 12자 SecureRandom 토큰** 발급 → QR로 태블릿 전달
- 키오스크 API 전체가 **토큰 스코프** (visitId 같은 추측 가능한 값을 경로에 두지 않음)
- 인증 없이 열리지만 **접근 대상이 접수 1건으로 한정**됨
- 토큰 만료 시각 존재

**평가**

| 항목 | 점수 |
|---|:---:|
| 신규성 | 낮음~중 — "별도 테이블에 저장"은 설계 선택으로 보일 수 있다 |
| 진보성 | 중 — 의무기록 무결성 + 장애 격리를 동시에 푼 점 |
| 구체성 | 중 |

**→ 단독 출원은 약하다. 후보 1·2의 종속항 또는 명세서 실시예로 쓴다.**

### 후보 4 — 종이 QR + 생년월일 2요소 비로그인 문서 열람 ★★

**해결한 문제.** 환자에게 계정을 만들게 하지 않고 증명서를 열람시켜야 한다.
QR만으로는 종이를 주운 사람이 열 수 있고, 계정을 만들게 하면 아무도 안 쓴다.

**구현한 수단** (`docshare/ShareAccessGuard.java`, `DocumentShareController`):

- 1요소: 종이에 인쇄된 **일회성 토큰 QR** (소지)
- 2요소: **생년월일 6자리** (지식)
- **토큰 단위** 무차별 대입 잠금: 5회 실패 / 10분 창

> 토큰별로 세는 게 핵심이다. IP 기준이면 병원 NAT 뒤 전체가 한 덩어리가 되고,
> 계정 기준이면 계정이 없어서 못 센다.

**평가**

| 항목 | 점수 |
|---|:---:|
| 신규성 | **낮음** — QR + 개인정보 확인은 택배·병원에서 흔하다 |
| 진보성 | 낮음~중 |

**→ 단독으로는 어렵다.** 다만 §4-C 보강(인쇄 시점 바인딩)을 넣으면 달라진다.

### 후보 5 — 경고 밴드 / 선택적 예측 ★

**논문의 주역이지만 특허로는 약하다.**

| 이유 |
|---|
| 임계값 비교·경고 표시는 **매우 일반적인 구성**이다 |
| "확신도가 낮으면 경고한다"는 아이디어 자체는 진보성을 인정받기 어렵다 |
| 우리 기여는 **측정으로 얻은 지식**이지 새로운 기술적 수단이 아니다 — 그건 논문의 영역 |

**→ 논문으로 간다.** 단, §4-B 보강(밴드 기반 트리아지 라우팅)을 구현하면
**특허 가능한 형태로 바뀐다.** 아래에서 설명한다.

## 3. 청구항 골격 (변리사 상담용 초안)

> ⚠️ 아래는 **상담 자료**이지 출원 서류가 아니다. 실제 청구항은 변리사가 선행기술을
> 조사한 뒤 작성해야 한다. 용어와 범위가 크게 달라진다.

### 후보 1 — 독립항 초안

> **[청구항 1]**
> 외부 네트워크에 위치한 서버와, 내부 네트워크의 출력 장치에 연결된 에이전트 단말을
> 포함하는 의료 문서 출력 중계 시스템으로서,
>
> 상기 서버는,
> (a) 출력 요청을 수신하여 출력 작업을 생성하고 상기 작업에 **유효 기간**을 설정하는 단계;
> (b) 상기 에이전트 단말로부터의 **아웃바운드 작업 요청을 지연 응답 상태로 보류**하고,
>     출력 작업이 생성되면 상기 보류된 요청에 해당 작업을 반환하는 단계;
> (c) 상기 작업 반환 시 상기 에이전트 단말의 **인스턴스 식별자를 상기 작업에 결합**하는 단계;
> (d) 상기 에이전트 단말로부터 수신한 결과 보고의 인스턴스 식별자가 (c)에서 결합된
>     식별자와 **불일치하는 경우 해당 결과를 폐기**하는 단계;
> (e) 상기 작업이 반환된 후 **소정 가시성 시간 내에 결과가 보고되지 않으면** 해당 작업을
>     재배달 가능 상태로 전환하는 단계;
> (f) 상기 유효 기간이 경과한 작업을 폐기하고, **상기 출력 요청을 발생시킨 업무 처리는
>     상기 폐기와 무관하게 완료 상태를 유지**하는 단계
> 를 수행하는 것을 특징으로 하는 시스템.

**종속항 방향**
- (c)(d)의 인스턴스 식별자가 에이전트 기동 시마다 새로 생성되는 난수인 경우 → **중복 출력 방지**
- 작업이 접수증·진료요약·증명서 중 하나의 유형을 갖고 유형별로 유효 기간이 다른 경우
- 후보 3의 키오스크 토큰이 출력물에 QR로 포함되는 경우
- 출력 실패 시 사용자에게 반환되는 메시지가 업무 중단 없이 표시되는 경우

### 후보 2 — 독립항 초안

> **[청구항 1]**
> 진료 기록으로부터 의료 증명 문서의 초안을 생성하는 방법으로서,
>
> (a) 저장부로부터 상기 진료 기록의 **사실 정보**(상병명, 질병분류코드, 진료 일자)와
>     **서술 대상 정보**를 획득하는 단계;
> (b) 상기 사실 정보 중 개인식별정보를 **마스킹**하여 프롬프트를 구성하는 단계;
> (c) 상기 프롬프트와 함께, **서술 필드만으로 구성되고 상기 사실 정보에 대응하는 필드를
>     포함하지 않는 응답 스키마**를 언어 모델에 제공하는 단계;
> (d) 상기 언어 모델의 응답 중 **상기 응답 스키마에 정의된 서술 필드만을 수용**하는 단계;
> (e) 상기 저장부의 사실 정보와 (d)의 서술 필드를 결합하여 문서를 구성하되,
>     **상기 사실 정보는 상기 언어 모델의 응답과 무관하게 상기 저장부의 값으로 확정**되는 단계;
> (f) 상기 언어 모델의 응답 획득에 실패한 경우, **서술 필드를 공란으로 하여 문서 구성을
>     계속 진행**하는 단계
> 를 포함하는 방법.

**이 청구항의 요점은 (c)와 (e)다** — "지어내지 말라고 시킨다"가 아니라
**"지어낸 값이 문서에 도달할 경로가 구조적으로 없다"**를 청구한다.

## 4. 특허성을 높이려면 지금 추가로 구현할 것 (아이디어 5)

> 사용자 요청: *"없다면 개선하고 도입해서 진행해볼만한 아이디어 제시"*
> 아래는 **구현 난이도 대비 특허 가치**가 높은 순서다.

### 🥇 A. LLM 출력 사후 검증 게이트 (사실 대조기)

**지금의 한계.** 후보 2는 사실 필드를 **스키마에서 뺐다**. 그런데 LLM이 **서술 칸 안에**
"흑색종 의증으로 판단됨"처럼 병명을 써 넣으면 그대로 통과한다. 구조적 차단에 **구멍이 있다.**

**추가할 것.** 서술 필드를 문서에 넣기 전에 **사실 대조 검증기**를 통과시킨다:

```
  LLM 서술 응답
      │
      ▼
 ┌──────────────────────────────────────────────┐
 │ 검증기                                        │
 │  1. KCD 상병명 사전 + 질병 마스터로 서술 내  │
 │     등장하는 병명 토큰을 추출                 │
 │  2. 추출된 병명이 DB 확정 진단과 일치하는가?  │
 │       불일치 → 해당 문장 제거 또는 초안 거부  │
 │  3. 날짜 패턴 추출 → 진료 기간 밖이면 거부    │
 │  4. 수치(일수·주수) 추출 → 허용 범위 밖 거부  │
 └──────────────────┬───────────────────────────┘
                    ▼
            검증 통과 서술만 문서에 반영
                    │
            거부 시 → 사유를 사용자에게 표시
                     (의사가 직접 작성하도록 유도)
```

| 왜 가치가 큰가 | |
|---|---|
| **특허** | 후보 2의 독립항을 **"생성 시 차단 + 생성 후 검증"의 이중 게이트**로 강화한다. 단독 독립항으로도 성립 가능 |
| **실용** | 실제로 있는 구멍을 막는다. 시연에서 "환각 어떻게 막나요" 질문에 답이 완전해진다 |
| **구현** | **중간.** KCD 마스터가 이미 DB에 있다(`backend/src/main/resources/data/`). 병명 사전 매칭 + 정규식 날짜 추출이면 1차 버전이 나온다 |
| **부수 효과** | 검증 거부율을 측정하면 **그 자체가 논문 재료**가 된다 |

**→ 가장 추천한다.** 특허·실용·시연 데모 값어치가 전부 있다.

### 🥈 B. 경고 밴드 기반 2단계 트리아지 라우팅

**지금의 한계.** 확신도가 낮으면 **화면에 배지를 띄우는 것**이 전부다. 그건 표시이지
시스템 동작이 아니다 — 그래서 특허가 안 된다.

**추가할 것.** 밴드에 따라 **처리 경로 자체를 바꾼다:**

```
  예비분석 결과의 확신도
      │
      ├─ 높음 (≥0.60)      → 통상 큐. 접수증에 표준 안내
      │
      ├─ 경고 밴드 (0.45~0.60) → ① 자동 재촬영 요청 (키오스크에서 1회 더)
      │                          ② 재촬영 결과와 1차 결과를 함께 저장
      │                          ③ 두 결과가 불일치하면 우선 검토 플래그
      │
      └─ 낮음 (<0.45)      → ① 추가 각도/조명 촬영 유도
                             ② 의사 대시보드에서 상단 고정
                             ③ 접수증에 "정밀 확인 필요" 표기
```

| 왜 가치가 큰가 | |
|---|---|
| **특허** | "표시"가 아니라 **"불확실성 구간에 따라 데이터 수집 절차와 업무 라우팅을 분기하는 방법"**이 된다. 구체적 기술 수단이 생긴다 |
| **논문 시너지** | §4-3의 "밴드 안에 오답이 2.6배 농축"이 **이 설계의 근거 데이터**가 된다. 논문이 특허의 실험적 뒷받침이 되는 이상적인 형태 |
| **구현** | **중간.** 키오스크 화면 분기 + `preliminary_analysis`에 재촬영 회차 컬럼 추가 |
| **주의** | 재촬영을 무한 요구하면 환자가 지친다. **1회로 제한**하는 것 자체가 종속항 소재 |

**→ 논문과 특허를 동시에 챙기는 유일한 아이디어다.**

### 🥉 C. 인쇄 시점 바인딩 문서 토큰 (후보 4 보강)

**지금의 한계.** QR 토큰은 발급 시점에 만들어져 만료까지 유효하다. 종이를 잃어버려도
시스템은 모른다.

**추가할 것.** 토큰의 생명주기를 **물리적 인쇄 사건에 묶는다:**

| 규칙 | 설명 |
|---|---|
| **인쇄 성공 보고 시점에 활성화** | 인쇄가 실제로 나왔다는 에이전트 보고(후보 1의 (d))를 받기 전까지 토큰은 비활성. **인쇄 실패 시 토큰이 살아 있는 상태 자체가 없다** |
| **재발급 시 이전 토큰 자동 무효화** | 증명서 재발급(`reissue`)이 일어나면 직전 종이의 토큰을 즉시 죽인다. 구권 종이가 계속 열리는 문제를 막는다 |
| **첫 성공 열람 후 단축 만료** | 한 번 열리면 남은 유효기간을 크게 줄인다 (예: 24시간) |
| **열람 이력 기록** | 언제 몇 번 열렸는지 남긴다 — 감사추적 부재 문제도 일부 해소 |

**→ 후보 1(인쇄 결과 보고)과 후보 4(문서 토큰)를 결합**해 하나의 독립항을 만들 수 있다.
두 요소가 원래 따로 있던 것을 엮는다는 점에서 진보성 논거가 생긴다.

**구현 난이도: 낮음.** 토큰 상태 컬럼 + 인쇄 결과 핸들러에 훅 하나.

### 4. D. 오프라인 내성 키오스크 큐잉

**해결할 문제.** 부스나 의원 대기실에서 네트워크가 끊기면 태블릿 촬영이 통째로 실패한다.

**추가할 것.**
- 태블릿이 촬영 이미지를 로컬(IndexedDB)에 큐잉하고, 연결 복구 시 **토큰과 함께 재전송**
- 서버는 **멱등 키**로 중복 업로드를 병합
- 큐 항목에 **촬영 시각**을 기록해 서버 수신 시각과 분리 저장

| 평가 | |
|---|---|
| 특허 | **중.** 오프라인 우선 동기화는 잘 알려진 패턴이라 신규성이 약하다 |
| 실용 | **높음.** 부스 시연 안정성이 크게 오른다 |

**→ 특허보다 실용 목적으로.** 명세서 실시예로는 쓸 수 있다.

### 5. E. 모델 버전 - 판독 결과 불변 결합

**해결할 문제.** 모델을 교체하면 과거 판독 결과의 근거가 사라진다. 의료 AI에서는
**"그때 어떤 모델이 무엇을 보고 그렇게 말했는가"**가 나중에 문제가 된다.

**이미 있는 것**: `MODEL_VERSION = efficientnet_b0-{sha256 앞 12자}` —
모델 파일 해시에서 버전을 유도한다. **파일이 바뀌면 버전이 저절로 바뀐다.**

**추가할 것**:
- 판독 결과 레코드에 `model_version` + `threshold` + `전처리 파라미터`를 **함께 불변 저장**
- Grad-CAM 히트맵도 같은 레코드에 결합
- 모델이 바뀐 뒤 같은 이미지를 재판독하면 **두 판독을 나란히 보관** (덮어쓰지 않음)
- 문서 발급 시 어떤 모델 버전의 판독에 근거했는지 표기

| 평가 | |
|---|---|
| 특허 | **낮음~중.** 버전 기록 자체는 흔하다. **"해시 유도 버전"과 "재판독 병행 보관"**의 조합이 쟁점 |
| 실용 | **매우 높음.** `docs/emr-meeting-brief.md`에서 지적된 **감사추적·원본보존 부재**를 직접 메운다 |

**→ 특허보다 제품 신뢰성 목적으로. 하지만 EMR 심사 대응에는 이게 제일 중요할 수 있다.**

## 7. 마지막 — 솔직한 평가

**이 프로젝트에 특허가 될 만한 게 있다는 판단은 유지한다.** 다만 과대평가하지 말아야 할 점:

| 현실 |
|---|
| 후보 1·2 모두 **선행기술 조사 전까지는 가능성일 뿐**이다. 비슷한 게 이미 있을 수 있고, 그건 검색해 봐야 안다 |
| 등록까지 보통 **1.5~3년**이 걸린다. 캡스톤 기간 안에 "특허 등록"은 불가능하고, **"특허 출원"까지가 현실적 목표**다 |
| 출원만으로도 이력·평가에서 값을 한다. 그걸 목표로 삼는 게 맞다 |
| §4의 보강 아이디어를 **구현하지 않고 아이디어만으로 출원**하는 것도 가능하지만, 구현된 쪽이 명세서가 훨씬 단단해진다 |

**가장 아까운 시나리오는 이것이다** — 저장소를 공개해 두고, 학회에서 발표하고,
1년이 지난 뒤에 "특허 낼걸" 하는 것. **§6의 첫 번째 블록(이번 주 할 일)만이라도
지금 해 두면 선택지가 열린 채로 남는다.**
