## 왜 평가 하네스가 필요했나

이 저장소에는 "이 모델이 얼마나 맞히는가"를 답할 수단이 없었다. 그래서

- 모델을 갈아끼웠을 때 **나아졌는지 나빠졌는지 판단할 근거가 없었고**,
- 신뢰도 임계값 기본값 `0.45` 가 왜 하필 0.45 인지 아무도 설명할 수 없었으며,
  (이 하네스로 실측한 뒤 0.35 로 내렸고, 이어서 **차단 자체를 없앴다** —
  지금 `LOW_CONFIDENCE_THRESHOLD` 는 차단선이 아니라 경고선이다)
- torch 버전을 올린 뒤 확률이 달라진 것을 눈으로만 확인했다.

모델을 손대기 전에 이것부터 있어야 한다. 기준선이 없으면 "바꿨다"는 있어도 "좋아졌다"는 없다.

## 홀드아웃 이미지를 저장소에 넣지 않는 이유

이미지 자체는 커밋하지 않는다. HAM10000 은 CC BY-NC 라 재배포 조건이 걸려 있고,
수천 장을 넣으면 git 저장소가 감당하지 못한다.

대신 **어떤 이미지를 평가에 썼는지 목록만** 텍스트로 고정한다(`holdout.csv`, 수십 KB).
목록이 고정돼 있으면 반년 뒤 다른 사람이 같은 수치를 다시 낼 수 있다.
이 저장소의 공식 목록은 `baselines/holdout.csv` 다.

> ⚠️ 학습에 쓴 이미지로 평가하면 안 된다. 점수는 올라가지만 그 점수는 거짓말이다.

### 목록은 학습과 평가가 공유한다

`baselines/holdout.csv` 는 **학습 노트북과 평가 스크립트가 같이 보는 한 장의 목록**이다.

- 학습(`notebooks/pad_ham_training.ipynb` 6번 셀): 이 목록의 사진을 학습에서 **뺀다**
- 평가(`evaluate.py`): 이 목록의 사진으로 점수를 **매긴다**

한 파일이 양쪽을 정의하니 둘이 어긋날 수가 없다. 예전처럼 노트북이 매번 새로 나누고
그 결과를 아무도 저장하지 않으면, 나중에 재는 점수가 진짜 실력인지 외운 걸 다시 맞힌
건지 구분할 방법이 사라진다. 실제로 그 일이 일어났다 — 전말은
[`baselines/README.md`](baselines/README.md).

> **그래서 이 목록을 함부로 고치지 말 것.** 고치는 순간 `baselines/` 의 기록들과
> 비교가 성립하지 않는다. `test_model_contract.py` 의 [4] 항목이 장수와 중복을
> 감시하고, 노트북이 다시 "매번 새로 분할" 로 되돌아가는 것도 여기서 막는다.

### 이 목록은 어떻게 나왔나 — `make_holdout.py`

현재 `fastapi/model.pth`(`efficientnet_b0-03061a31e63f`)를 학습할 때 쓴 분할 목록은
파일로 남지 않았다. 하지만 `notebooks/pad_ham_training.ipynb` 의 분할이
**시드가 고정된 결정적 연산**이라 절차를 그대로 재현하면 목록을 되살릴 수 있다.

```
StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=42)
```

`make_holdout.py` 가 그 노트북의 5번·6번 셀을 그대로 옮긴 것이다. 세 데이터셋의
메타데이터만 있으면 홀드아웃 2,857장(전체 14,285장의 1/5) 목록이 나온다.

```bash
# pandas / scikit-learn 이 필요하다 — 추론 이미지에는 없으므로 컨테이너 밖에서 돌린다
python3 tests/make_holdout.py \
  --ham-dir  ~/Downloads/CapstoneDesign/archive \
  --pad-dir  ~/Downloads/pad-work/pad-ufes-20-small \
  --scin-dir ~/Downloads/scin-work/scin-small \
  --out /tmp/holdout.csv --verify
```

> 이 스크립트는 **목록을 처음 만들 때 한 번** 쓰는 것이다. 평소에는 다시 돌릴 일이
> 없다 — 돌리면 `baselines/holdout.csv` 와 다른 목록이 나올 수 있고, 그러면 지금까지의
> 기준 결과와 비교가 깨진다. 데이터셋을 새로 구성해 목록 자체를 다시 정할 때만 쓴다.

**복원이 맞았는지는 확정하지 못했다.** `--verify` 로 학습분(11,428장)도 같이 쟀는데
84.84% 대 83.86%, 격차가 표준오차 안이라 판정이 안 됐다. 다만 **모델이 자기가 학습한
사진에서도 84.84% 밖에 못 맞힌다**는 사실이 오염의 상한을 준다 — 외우지 않았으므로
오염이 있어도 점수를 1%p 이상 부풀리지 못한다. 자세한 논증은
[`baselines/README.md`](baselines/README.md).

**데이터셋별로 나눠 보기** — `holdout.csv` 의 `src` 열로 걸러 따로 재면
출처별 성능이 보인다. `pad`(스마트폰 촬영)가 실제 키오스크 환경에 가장 가깝고,
`ham`(더모스코피)보다 어렵다.

## 임계값의 나머지 절반 — 병변이 아닌 사진 (OOD)

임계값이 원래 맡았던 일은 정확도를 올리는 게 아니라 **피부 병변 사진이 아닌 것을
걸러내는 것**이었다. 못 미치면 진단 대신 "피부 병변 이미지로 판단하기 어렵습니다"가
떴다.

그런데 홀드아웃은 전부 진짜 병변 사진이다. 거기서 나오던 거절률은 하나같이
**오거절률** — 그 차단의 *비용*이었다. 효과는 그 데이터로 영영 측정되지 않는다.
0.45 를 0.35 로 내린 결정도 그 절반짜리 표를 근거로 했다. 벽 사진이 `mel 40%` 로
통과해도, 기존 측정에는 아무것도 나타나지 않았다.

`make_ood.py` 가 나머지 절반을 만든다. 여기 있는 사진은 **전부 걸러지는 것이 정답**이다.

**그리고 이 세트가 차단을 없앴다.** 나머지 절반을 재 보니 0.35 에서 OOD 의 79.6% 가
그냥 통과했다 — 걸러내라고 둔 장치가 걸러내지 못했다. 반대편 비용은 선명했다:
차단이 있으면 흑색종 재현율이 89.3% → 88.8% 로, 0.45 로 올리면 86.3% 까지 떨어졌다.
애매한 것부터 걷어내는데 하필 애매한 쪽에 암이 몰려 있었기 때문이다. 못 하는 일을
하겠다고 암을 놓치고 있었으므로 차단을 걷어내고 **경고**로 바꿨다. 아래 표들은
그래서 지금 "걸러졌다"가 아니라 "경고가 붙었다"를 센다.

### 갈래

| 갈래 | 무엇 | 재현 |
|------|------|:---:|
| `normal_skin` | 정상 피부. PAD 홀드아웃 사진의 모서리 크롭. | ✅ |
| `degenerate` | 촬영 실패 — 렌즈 가림, 과노출, 초점 실패, 저조도 노이즈, 손떨림. | ✅ |
| `pattern` | 사물·직물·문서 — 줄무늬, 체크, 텍스트, 격자. | ✅ |
| `surface` | 나무결·골판지·시멘트·모래·가죽·직물. 색은 피부색인데 피부가 아닌 것. | ✅ |
| `photo` | 비피부 실사진. `--photo-dir` 를 줄 때만. | ❌ 로컬 파일 |

**`normal_skin` 이 이 세트의 핵심이다.** 새까만 화면에서 확신이 낮은 건 당연하다.
키오스크에서 실제로 일어나는 오촬영은 *아무것도 없는 팔뚝을 찍는 것*이고,
그건 색도 질감도 학습 데이터와 똑같아서 모델이 "피부처럼 생겼으니 병변"이라고 답하기
가장 쉬운 입력이다. 그래서 갈래를 나눈다 — 합치면 쉬운 쪽이 어려운 쪽을 가린다.

`surface` 를 따로 둔 이유도 같다. `pattern`(줄무늬·격자·문서)은 규칙적인 고주파
무늬라 피부와 통계가 확연히 달라서 사실 쉬운 문제다. 어려운 건 **색은 피부색인데
피부가 아닌 것** — 책상 나뭇결, 골판지 상자, 시멘트 벽이다. 측정해 보니 실제로
`surface` 의 경고율이 `pattern` 보다 낮았다 (0.35 기준 16.7% vs 26.1%).

`normal_skin` 을 **홀드아웃 PAD 사진에서만** 뽑는 이유가 둘 있다. 모델이 그 피부를
한 번도 본 적이 없다는 것이 보장되고(학습 사진의 모서리를 쓰면 "처음 보는 정상 피부"를
재는 게 아니게 된다), 출처가 `baselines/holdout.csv` 라 누구든 같은 크롭을 다시
만들 수 있다.

### 만들기

이미지는 커밋하지 않는다 — `holdout.csv` 와 같은 이유(라이선스·저장소 크기)다.
대신 **생성기가 결정적**이라, 같은 명령이 같은 그림을 다시 만든다.
(`ood_manifest.csv` 가 함께 나온다. 어느 PAD 사진의 어느 모서리인지까지 적혀 있다.)

```bash
docker run --rm \
  -v "$PWD/fastapi/tests:/app/tests:ro" \
  -v ~/Downloads/pad-work/pad-ufes-20-small/images:/pad:ro \
  -v /만들_경로:/ood \
  -e INTERNAL_API_SECRET=dummy \
  artifact-medical-ai-fastapi \
  python tests/make_ood.py --pad-dir /pad --out /ood
```

### 이 세트가 하지 못하는 것

정직하게 적어 둔다. 이 한계를 모르면 숫자를 과신하게 된다.

- **`normal_skin` 이 100% 깨끗하지는 않다.** 선별을 통과한 391장 중 96장을 무작위로
  골라 눈으로 확인했더니 5장 정도(약 5%)가 애매했다 — 각질 낀 가장자리, 오돌토돌한
  융기, 번들거리는 점막 같은 것들이다. 피부과 전문의 판정이 아니라 육안 판정이다.
  그래서 이 갈래의 통과율은 모델 실패의 **상한**으로 읽어야 한다.
- **출처가 치우쳐 있다.** 병변을 찍으려고 든 카메라의 가장자리라, 평균적인 피부보다
  햇빛 손상이 많고 나이 든 피부 쪽으로 기운다.
- **`degenerate`·`pattern`·`surface` 는 합성이다.** 실제 손·얼굴·옷·음식 사진이 아니다.
  재현되고 라벨이 확실하다는 장점과, 실제 카메라의 통계가 아니라는 단점을 같이 가진다.
  진짜 카메라로 찍은 비피부 사진 100~200장이 있으면 `--photo-dir` 로 넣는 편이 낫다.
- **`photo` 갈래는 재현되지 않는다.** 로컬 파일에서 오므로 **기준값에는 넣지 않는다.**
  커밋된 `baselines/ood-*.json` 은 재현되는 네 갈래만으로 만든다 — 기준값은 남이 다시
  만들어 대조할 수 있어야 의미가 있는데, 내 노트북에만 있는 파일이 섞이면 그게 안 된다.

### 정상 피부 모서리를 고르는 기준

`_corner_score()` 가 네 모서리를 각각 재서 셋 다 통과한 것 중 가장 깨끗한 하나를 고른다.
숫자는 PAD 홀드아웃 459장 × 네 모서리 = 1836개를 실제로 측정하고 구간별 크롭을 눈으로
보면서 정했다.

| 기준 | 값 | 왜 |
|------|----|----|
| 피부색 픽셀 비율 | ≥ 0.90 | 채널 *평균*만 보면 절반이 배경(천·풀·머리카락)인 모서리도 통과한다. 측정된 분포가 통과 [0.62/0.94/1.0], 탈락 [0.03/0.16/0.30] 으로 갈려서 0.90 은 빈 구간에 있다. |
| 파란 잉크 픽셀 비율 | ≤ 0.02 | 시술 표시용 펜 자국. 피부에는 B ≥ R 인 픽셀이 사실상 없다. |
| 어두운 얼룩 깊이 | ≤ 20 | 점·주근깨·굵은 혈관. 대역통과(가는 블러 − 굵은 블러)로 잰다. |

세 번째를 대역통과로 재는 게 핵심이다. 그냥 "가장 어두운 픽셀"로 재면 순위를 처음부터
끝까지 **털**이 결정한다 — 털 많은 피부도 정상 피부인데 그것만 잘려나가 세트가 민머리
피부로 치우친다(실제로 그렇게 나왔다). 가는 블러가 털을 지우고, 굵은 블러를 빼면 조명
기울기와 비네팅이 빠진다. 남는 것이 딱 점 크기의 얼룩이다.

기준을 조인 결과 443장 → 391장이 됐는데, **빠진 52장은 대부분 모델이 `bkl`
(지루각화증 = 색소 얼룩)로 부르던 것들이었다.** 얼룩을 골라내는 필터가 실제로 얼룩을
골라냈다는 방증이다.

## 실행

컨테이너 안에서 돌린다. 전처리(Resize·Normalize)를 `main.py` 에서 그대로 가져다 쓰기 때문에
**실제로 서빙되는 것과 똑같은 조건**으로 측정된다. 값을 복사해 두면 언젠가 한쪽만 바뀌고,
그때부터 이 평가는 서빙되지 않는 다른 모델을 재게 된다.

### 계약 테스트 — 데이터 없이 지금 바로

```bash
docker compose exec -T fastapi python tests/test_model_contract.py
```

백엔드 마이그레이션까지 대조하려면 저장소를 통째로 붙여서 돌린다
(컨테이너 이미지에는 `fastapi/` 만 들어 있어 백엔드 소스가 없다):

```bash
docker run --rm -v "$PWD:/repo:ro" -w /repo/fastapi \
  -e INTERNAL_API_SECRET=contract-test \
  artifact-medical-ai-fastapi python tests/test_model_contract.py
```

### 평가 — 홀드아웃 이미지가 있을 때

호스트의 데이터 폴더를 `/data` 로 붙인다. `docker-compose.yml` 은 건드리지 않는다.

**(1) 이미지 폴더 + 목록 CSV** — 노트북이 만든 `holdout.csv` 를 쓰는 경우

```bash
docker compose run --rm -v /데이터경로:/data:ro fastapi \
  python tests/evaluate.py --image-dir /data/images --csv /data/holdout.csv
```

CSV 컬럼명 기본값은 HAM10000 기준(`image_id`, `dx`)이다. 다르면 `--id-col` / `--label-col`.
파일 확장자는 CSV 에 없어도 된다 — `.jpg`, `.png` 등을 알아서 찾는다.

`--image-dir` 는 폴더를 여러 개 받는다. HAM10000 배포본은 이미지가 두 폴더로 쪼개져 있는데
metadata.csv 는 하나라서 필요하다:

```bash
docker compose run --rm -v ~/Downloads/CapstoneDesign/archive:/data:ro fastapi \
  python tests/evaluate.py \
    --image-dir /data/HAM10000_images_part_1 /data/HAM10000_images_part_2 \
    --csv /data/HAM10000_metadata.csv --batch-size 64
```

> ⚠️ 위 명령은 **HAM10000 전체**를 재는 것이라 학습에 쓴 이미지가 섞여 있다.
> 나오는 수치는 진짜 성능이 아니라 낙관적인 상한선이다. 정식 측정은 `--csv` 에
> `baselines/holdout.csv` 를 주는 아래 방식으로 한다.

**(2) 클래스별 하위 폴더** — `/data/mel/*.jpg`, `/data/nv/*.jpg` …

```bash
docker compose run --rm -v /데이터경로:/data:ro fastapi \
  python tests/evaluate.py --image-dir /data
```

### 평가 — 병변이 아닌 사진 (OOD)

```bash
docker compose run --rm -v /만든_경로:/ood:ro fastapi \
  python tests/evaluate.py --ood-dir /ood
```

하위 폴더 이름이 갈래가 된다. 라벨은 필요 없다 — 정답은 언제나 "경고가 붙는 것"이다.

병변 홀드아웃과 **함께** 주면 임계값의 양쪽 비용을 한 표에 놓고 본다.
이 표가 OOD 를 붙인 이유다:

```bash
docker compose run --rm \
  -v ~/Downloads/CapstoneDesign/archive:/ham:ro \
  -v /만든_경로:/ood:ro \
  fastapi python tests/evaluate.py \
    --image-dir /ham/HAM10000_images_part_1 /ham/HAM10000_images_part_2 \
    --csv tests/baselines/holdout.csv --label-col label \
    --ood-dir /ood
```

### 모델을 교체할 때 — 이게 원래 목적이다

```bash
# 1. 지금 모델의 성적을 남긴다
docker compose run --rm -v /데이터경로:/data fastapi \
  python tests/evaluate.py --image-dir /data --csv /data/holdout.csv \
  --json /data/before.json

# 2. fastapi/model.pth 를 새 가중치로 교체하고 다시 빌드
docker compose build fastapi && docker compose up -d fastapi

# 3. 같은 데이터로 다시 재고 비교
docker compose run --rm -v /데이터경로:/data fastapi \
  python tests/evaluate.py --image-dir /data --csv /data/holdout.csv \
  --compare /data/before.json
```

`model_version`(가중치 파일의 SHA256 앞 12자리)이 결과에 함께 찍히므로,
어떤 가중치의 성적인지 나중에도 헷갈리지 않는다.

지금까지 잰 값은 `baselines/` 에 있다. 현재 모델의 기준선은
`baselines/holdout-2026-08-30.json`(공식 홀드아웃 2,857장, 83.86%)과
`baselines/ood-2026-08-30.json`(병변 아닌 사진 543장, 0.35 기준 경고율 20.44%)이다.
`ham10000-full-2026-08-30.json` 은 학습 이미지가 섞인 옛 측정이라 참고용이다.
세 값의 관계와 신뢰 범위는 `baselines/README.md` 에 적어뒀다.

## 보고서 읽는 법

**혼동행렬** — 행이 실제 병명, 열이 모델의 답. 대각선 밖에 몰려 있는 큰 수가 그 모델의 약점이다.
`mel` 행의 `nv` 열이 크다면 흑색종을 점이라고 말하고 있다는 뜻이다.

**놓치면 안 되는 것** — 악성·전암(`mel`·`bcc`·`akiec`)을 양성으로 판정한 비율.
전체 정확도가 아무리 높아도 이 값이 크면 임상적으로는 쓸 수 없는 모델이다.
심각도 기준은 `backend/.../V1__baseline_schema.sql` 의 `disease` 시드를 따랐다.

**클래스별 표의 경고율** — 그 병의 실제 사진 중 "확신 낮음" 경고가 붙은 비율.
전체 경고율만 보면 "몇 장 중 한 장에 경고가 붙는다"까지밖에 모른다. 그게 어느 병에
몰려 있는지가 훨씬 중요하다 — 흑색종에서만 경고가 잦다면, 그건 모델이 가장 위험한
병에서 가장 흔들린다는 뜻이다. (차단하던 시절에는 같은 숫자가 **가장 위험한 병에서만
입을 다문다**는 뜻이었다. 그래서 차단을 걷어냈다.)

**임계값 표** — `LOW_CONFIDENCE_THRESHOLD` 를 0.05 간격으로 훑는다. 임계값을 올리면
경고가 붙는 비율이 오르고, 경고가 안 붙은 결과의 정확도도 함께 오른다. 그 교환비를
보고 현재 값을 정한다. 기본값 0.45 는 원래 근거 없이 정해진 **차단선**이었고,
이 표를 근거로 0.35 까지 내렸다가 차단 자체를 없앴다. 지금 같은 자리에 있는 0.45 는
경고선이라 뜻이 다르다 — 근거는 `main.py` 의 해당 상수 주석에 있다.

읽을 때 주의할 것: 여기서 "경고율"은 **정상적인 병변 사진에 경고가 붙은 비율**이다.
차단이던 시절 이 숫자는 전부 오거절, 즉 순수한 비용이었다. 경고가 된 지금은 비용이
아니라 **화면이 시끄러워지는 정도**다 — 너무 높으면 아무도 경고를 안 읽게 되므로
여전히 낮을수록 좋지만, 답을 못 받는 사람은 이제 없다. 이 밴드가 값을 하는지는
밴드 안팎의 정확도 차이로 판단한다: 0.45 에서 밴드 안 57.3% vs 밖 88.3% 이고,
전체 오답의 38% 가 밴드 안 14.4% 에 들어 있다.

**OOD 표 (`--ood-dir`)** — 여기서는 부호가 뒤집힌다. 병변 사진이 아니므로 경고가
붙는 것이 정답이고, 경고율이 곧 정답률이다. 갈래를 나눠 보는 이유는 난이도가 전혀
다르기 때문이다 — 새까만 화면과 아무것도 없는 팔뚝은 같은 문제가 아닌데, 한 숫자로
합치면 쉬운 쪽이 어려운 쪽을 가린다. `위험군` 열은 경고 없이 지나간 것 중 악성·전암으로
분류된 장수다. 그냥 지나간 것보다 나쁘다 — 아무 표시 없이 화면에 전암 의심이 뜬다.

**「임계값의 양쪽 비용」 표** — 둘을 같이 주면 나온다. 왼쪽은 진짜 병변에 경고가
붙은 비율, 오른쪽은 병변 아닌 사진이 아무 표시 없이 병명을 받은 비율. 임계값을 올리면
왼쪽이 나빠지고 오른쪽이 좋아진다. 이 표를 처음 뽑고 알게 된 것은 **어느 값에서도
교환비가 성립하지 않는다**는 것이었다 — OOD 를 3분의 2 잡으려면 진짜 병변의 3분의 1에
경고를 붙여야 한다. 이 결론이 차단을 없앤 직접적인 근거다. 차단이었을 때는 저 3분의 1이
"답을 못 받는 환자"였지만, 경고인 지금은 "표시가 하나 더 붙는 환자"라 같은 교환비의
무게가 다르다. 수치는 [`baselines/README.md`](baselines/README.md).

`--min-mel-recall 0.7` 은 mel 재현율의 하한, `--max-ood-pass-rate 0.3` 은 OOD 무경고율의
상한이다. 미달·초과 시 종료코드 1 이라 CI 게이트로 쓸 수 있다. 다만 OOD 쪽은 현재
무경고율이 79.6% (0.35 기준)라 지금 걸면 무조건 실패한다 — 판별기를 붙인 뒤에 켤 게이트다.

## 자주 겪는 것

**`INTERNAL_API_SECRET` 관련 에러** — `main.py` 는 이 값이 없으면 기동을 거부한다.
두 스크립트는 포트를 열지 않으므로 값이 없으면 대체값을 쓴다. `docker compose run` 으로
돌리면 compose 가 실제 값을 넣어주므로 신경 쓸 일이 없다.

**"평가할 이미지가 하나도 없습니다"** — CSV 의 라벨이 `CLASSES` 에 없거나(예: HAM10000 원본에
`inflammatory` 는 없다) 파일을 못 찾은 경우다. 실행 직후 뜨는 ⚠ 줄에 건수와 예시가 나온다.

**추론이 느림** — 배포 대상에 GPU 가 없어 CPU 로 돈다. `--batch-size` 를 올리면 빨라진다.
Grad-CAM 은 확률에 영향이 없어 평가에서는 아예 건너뛴다.
